# MongoDB Atlas → JanusGraph and Cassandra migration

Date: 2026-09-07

Status: Infrastructure implementation started. Docker and local Kubernetes validation passed; home-cluster access and initial capacity preflight now pass; deployment is staged in infrastructure PR #3 and production recovery gates remain open. No application data migration performed. See [implementation evidence](2026-09-07-data-infrastructure-progress.md).

## Outcome and approach

Replace MongoDB Atlas with a self-hosted JanusGraph graph backed by Cassandra. Make Cartyx's campaign content addressable and connected: NPCs in a town, NPCs associated with a session, organization membership, quest participants, and wiki backlinks. Preserve the existing wiki and tabletop features while creating a foundation for richer relationships.

Start with infrastructure: Docker locally, then separate development and production deployments in Kubernetes through the existing GitOps workflow. Only after both environments pass persistence and recovery checks do we migrate application subsystems. Planned outages lasting several days are acceptable; preservation of existing data remains a requirement.

Use maintenance windows and a single authoritative backend per subsystem. Do not build a permanent Mongo/graph dual-write system. A phase is complete when its code, data, validation, and operational documentation are complete in dev and then prod. Keep later, dependent features unavailable where necessary until their phase is ready.

## Target architecture

```text
Browser → existing web / realtime endpoints
                   │
          application repositories
             ┌─────┴──────────────┐
             │                    │
       Gremlin client         CQL client
             │                    │
      JanusGraph Server           │
         │          │             │
         │     search index       │
         │   (Elasticsearch)      │
         │                        │
         └──────── Cassandra ─────┘
                    │
         graph keyspace + separate
         application-state keyspace

R2: existing media + private off-host database backups
Flux: separate dev and prod releases in the existing cluster
```

**Storage ownership:** JanusGraph owns entity content and relationships. Cassandra is its storage backend through `storage.backend=cql`; application code must never modify JanusGraph's internal tables. Dedicated application-owned CQL tables hold operational records whose access and concurrency requirements suit them: ordered room history, job leases, and selected conditional state. Give those tables a separate keyspace, schema migrations, and credentials. JanusGraph documents this remote server/CQL architecture in its [Cassandra backend guide](https://docs.janusgraph.org/storage-backend/cassandra/).

Every persisted field gets one authority. For example, an audio job row owns processing status and lease state, while an audio vertex owns wiki metadata and relationships. Graph summaries of operational state are derived projections, updated by an idempotent, recoverable process. R2 object deletion consults authoritative ownership and references, never a potentially stale projection alone.

**Search:** bring up JanusGraph and Cassandra first. Add a supported Elasticsearch mixed-index backend before migrating the first subsystem with full-text search. Exact identity lookup and relationship traversal can initially use composite and vertex-centric indexes. JanusGraph distinguishes these from mixed indexes needed for indexed text and range queries; Cassandra alone does not preserve Mongo `$text` behavior. [Index guidance](https://docs.janusgraph.org/v1.1/schema/index-management/index-performance/), [text-search semantics](https://docs.janusgraph.org/index-backend/text-search/).

**Versions:** Phase 0 must produce an exact tested matrix and pinned image digests for JanusGraph, Cassandra, JDK/container architecture, Gremlin JavaScript client, serializer, and Elasticsearch. The published JanusGraph 1.1 compatibility matrix lists Cassandra 3.11/4.0 and TinkerPop 3.7; this is a research baseline, not a recommendation to deploy an old bundled patch. Resolve compatibility against currently maintained/security-patched releases and test the selected combination; do not assume Cassandra 5, TinkerPop 4, or an OpenSearch substitution works. [JanusGraph compatibility and releases](https://docs.janusgraph.org/changelog/).

## Phase 4 — Graph foundation, search, and migration tooling

### Schema and relationship rules

Keep current API identifiers as strings: preserve each Mongo `_id` value as an application `entityId`; let JanusGraph manage its internal vertex IDs. Define a unique indexed identity tuple including entity kind and scope, with an explicit scope for global/user-owned records. Do not expose Gremlin IDs in routes or references. Retain existing ID format for newly created records while legacy ObjectId consumers remain, then change validators in a separate migration if desired.

Use explicit labels/property types/cardinality, disable accidental schema creation, and run versioned schema changes through a single migration job. Wait for index availability, reindex existing data when required, and fail production queries that require an unplanned full graph scan. Graph properties should hold queryable values and content; bounded nested UI values may use versioned JSON. Do not hide traversable relationships inside JSON.

| Meaning                                  | Proposed canonical relationship                                                                                                                  |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| Content belongs to a campaign            | `Entity → IN_CAMPAIGN → Campaign` plus indexed campaign scope                                                                                    |
| Building/neighborhood is inside a town   | `Location → WITHIN → Location`; incoming traversal replaces the duplicated child array                                                           |
| NPC's current location                   | `Character → LOCATED_IN → Location`                                                                                                              |
| NPC associated with a session            | `Character → ASSOCIATED_WITH → Session`, with source/reason/visibility                                                                           |
| Player or NPC belongs to an organization | Membership relation with title/public/private notes; preserve the membership's existing ID using a relation vertex where independently addressed |
| Quest giver/participant or hierarchy     | `GIVEN_BY`, `INVOLVES`, `SUBQUEST_OF`                                                                                                            |
| Wiki reference/backlink                  | `LINKS_TO` with relationship metadata; backlinks use incoming traversal                                                                          |
| Tagging                                  | `TAGGED_WITH` campaign-scoped normalized tag vertices                                                                                            |
| Map token represents an entity           | `REPRESENTS`; token placement remains an instance, not the identity of the NPC                                                                   |

Make all meaningful records linkable, but do not create all possible pairs. Define allowed endpoints, multiplicity, direction, visibility, deletion behavior, and provenance for each relationship type. Preserve ordering where UI arrays are ordered. Reify a relationship as a vertex when it needs its own ID, history, or multiple pieces of evidence.

`LOCATED_IN` means current placement. Residence and historical session placement need distinct semantics (`RESIDES_IN` or dated/session-linked occurrences); do not overwrite history when an NPC moves. A town query includes the town and nested locations with cycle protection, pagination, and authorization at every step. Session associations include explicit legacy references and supported event/document references; record why the NPC is associated rather than treating every mention as physical attendance.

Match free-text NPC locations only to an unambiguous same-campaign location. Preserve original text; produce unresolved/ambiguous mappings for manual correction. Reconcile contradictory parent/child arrays and deduplicate `sessionId`/`sessions` references without silently discarding provenance. Dangling references become reported migration exceptions, not fabricated entities.

Enforce campaign membership, entity visibility, relationship visibility, GM-only fields, and player edit permissions in server repositories. A visible NPC does not make a private relationship visible. Global SRD records and user-owned audio need explicit scope rules. Do not expose a general Gremlin endpoint to browsers. Search, totals, backlinks, and multi-hop paths must not reveal hidden entities or relationships.

### Application boundary and correctness

- [ ] Add server-only domain repositories under proposed `app/server/repositories/`, plus graph/CQL clients and codecs under `app/server/db/`. Preserve existing server function request/response DTOs. No Mongoose types in the new domain interfaces.
- [ ] Extract a Mongo adapter only when needed for the next slice; do not rewrite every model abstraction up front. Route each subsystem explicitly to Mongo, graph/CQL, or maintenance. No silent fallback to stale Mongo data.
- [ ] Install the search service in Compose and both data releases with the same persistence/security practices. Implement text/filter/sort parity tests before the first wiki slice; search ranking may differ, but no feature silently disappears.
- [ ] Define bounded traversals, stable pagination, batched fetching, timeout/cancellation/reconnect handling, and idempotency for retries with uncertain commit outcomes. Use client traversals/bound parameters, never interpolated user scripts. Separate schema/admin execution from runtime traversal access.
- [ ] Replace Mongoose defaults, validation, hooks, sparse/partial uniqueness, timestamps, projections, and error mapping explicitly. Inventory schemas directly: the existing index governance registry is not the complete collection list.
- [ ] Design uniqueness and conditional-state operations before moving auth or workers. JanusGraph on Cassandra does not provide Mongo-equivalent transaction isolation; graph locking requires deliberate configuration and has failure limits. [JanusGraph consistency guidance](https://docs.janusgraph.org/advanced-topics/eventual-consistency/).
- [ ] Use application-owned Cassandra lightweight transactions for selected compare-and-set invariants: key reservations, revisioned control state, and job fencing. Define partition keys, contention limits, serial/read/write consistency, retry behavior, and reservation recovery. These are not arbitrary cross-partition transactions. [Cassandra guarantees](https://cassandra.apache.org/doc/stable/cassandra/architecture/guarantees.html).
- [ ] For multi-record operations, specify one authoritative control record plus recoverable/idempotent steps. Examples: campaign creation, membership changes, one active session, screen reorder, and graph/job projections. Return success only at the documented committed state; repair incomplete work after crashes. Never infer authorization from a stale graph projection when authoritative membership has been revoked.

**Exit:** schema/clients/migrator work against actual containers and dev Kubernetes; search is deployed; repository contract, isolation, duplicate-write, and failure-recovery tests pass. Production code remains on its previous subsystem authorities until each cutover below.

## Repeatable cutover and rollback procedure

1. **Prepare:** pin source/target application, schema, data chart, and image revisions; record a per-environment manifest of authoritative backends. Rehearse on synthetic or appropriately sanitized data and measure migration time. Never seed dev directly with production secrets or private content.
2. **Quiesce:** put the slice and dependent mutations into maintenance; use whole-app maintenance if dependencies cannot be isolated safely. Drain/stop affected workers, WebSocket writes, seed scripts, cleanup jobs, and old app replicas. Record zero remaining writers. Express sustained maintenance/replica changes in GitOps so Flux cannot undo them.
3. **Capture:** take a restorable Atlas export/backup suitable for the actual tier plus a target checkpoint. Export raw data with BSON/Extended JSON type fidelity, preserving IDs, timestamps, null-versus-missing, nested arrays, secrets, and all required fields. Hash/count each collection. No committed dumps or secrets.
4. **Transform:** load vertices first, then edges and CQL records. Use deterministic identities, checkpoints, bounded batches, retries, a reference ledger and quarantine reports. Re-running after interruption must not duplicate vertices, relationships, jobs, or history. Upsert alone does not handle source deletions: reconcile removals against the frozen source manifest and tombstone/delete stale target records deliberately.
5. **Validate:** compare all relevant property values using normalized hashes, entity counts by kind/campaign, edge counts by label, timestamps, media keys, and orphan reports. Map each source index/constraint to its replacement. Run permission, search, CRUD, ordering, relationship, concurrency, restart, and recovery checks. Resolve/quarantine every discrepancy explicitly; global counts alone are insufficient.
6. **Switch:** activate the slice's backend and deploy compatible web/worker/realtime consumers together as required. Smoke-test against actual target storage, then reopen traffic. Record completion in the migration manifest and take a post-cutover backup.
7. **Observe:** verify errors, search/index freshness, latency, queue progress, and data reconciliations against agreed limits. Use representative campaign-size load tests; set performance thresholds from measured existing behavior before each slice.

Before reopening writes, rollback can restore the target checkpoint and reactivate the frozen Mongo slice. After new writes are accepted, flipping a flag back to Mongo would lose data. Re-enter maintenance and either repair forward (default) or run a rehearsed reverse export/replay that preserves all accepted writes. Keep an application-owned operation journal/checkpoint for migrated mutations when reverse rollback is required; define how it remains recoverable if graph and journal updates fail between steps. Do not promise lossless reverse migration without demonstrating it.

Leave old Mongo collections frozen for the agreed retention period; do not delete collections during individual code PRs. Expanding an old subsystem back into service requires reference reconciliation with already migrated subsystems.

## Completion criteria

- Local Docker, optional kind, Kubernetes dev, and Kubernetes prod all run the same tested storage architecture and schema versions.
- Every existing persisted collection has a documented destination and verified import; every production read/write path uses the new storage. No runtime Mongo requirement remains in web, realtime, audio worker, fixtures, or operational tooling.
- Demonstrate: all visible NPCs in a town including nested buildings; all visible NPCs associated with a session; organization memberships; quest participants; and wiki backlinks. Moving an NPC does not rewrite historical session facts.
- Permission tests prove no cross-campaign access or disclosure through private edges, search snippets/totals, GM fields, or backlinks.
- Re-run imports and interrupted operations without duplicates; enforce identity/active-session/worker-fencing constraints under concurrency; pass multi-browser tabletop and audio scenarios.
